# Lore on AWS: beginner guide

Everything here is plain CloudFormation plus one shell script. No Terraform, no CDK, no Lambda, no custom resources. The plan and the reasons behind it are in [`docs/INFRA_PLAN.md`](../docs/INFRA_PLAN.md); day-to-day commands are in [`docs/RUNBOOK.md`](../docs/RUNBOOK.md) section 8.

## The picture in one paragraph

A visitor opens one HTTPS address (`https://dxxxx.cloudfront.net`). **CloudFront** serves the React page from a private **S3** bucket, and forwards every `/api/*` call to an **Application Load Balancer**. The load balancer only forwards requests that carry a secret header (which only our CloudFront adds) and sends them to a single **ECS Fargate** task. That task holds two containers that share `localhost`: our FastAPI app and **FalkorDB**. FalkorDB writes its files to an **EFS** disk, so the graph survives restarts. The app keeps its keys in **Secrets Manager**, and its image is built by **CodeBuild** and stored in **ECR**.

```
Browser --HTTPS--> CloudFront --/*--------> S3 (React build, private, via OAC)
                       |
                       +--/api/* (+ secret header, HTTP)--> ALB --8000--> ECS Fargate task (ARM64)
                                                                           |  api container  --localhost:6379--> falkordb container
                                                                           |                                         |
                                                                           +-------------------- NFS --------------> EFS
```

## What gets created (four stacks)

| Stack | File | What is in it |
|---|---|---|
| `lore-network` | `cfn/network.yaml` | A VPC with two public subnets, an internet gateway (no NAT gateway, to save about $1 a day) and three security groups (firewalls): ALB (port 80 from CloudFront's IP list only), task (port 8000 from the ALB only), EFS (port 2049 from the task only). |
| `lore-registry` | `cfn/registry.yaml` | The ECR repository `lore-api`, an S3 bucket `lore-artifacts-<account>` for the build zip, a CodeBuild project that builds the ARM64 image, and two secrets: `lore/app` (your keys) and `lore/origin-verify` (random, generated by CloudFormation). |
| `lore-app` | `cfn/app.yaml` | The ECS cluster, task definition (two containers) and service, the load balancer, the EFS disk, two IAM roles and two log groups. |
| `lore-frontend` | `cfn/frontend.yaml` | The private S3 bucket `lore-web-<account>` and the CloudFront distribution. |

Names all start with `lore-` because the deploying user's IAM policy ([`iam/lore-deployer-policy.json`](iam/lore-deployer-policy.json)) only allows `lore-*` roles and buckets and `lore/*` secrets.

Every template has one short comment per resource saying why it exists.

## Before the first deploy

1. **AWS CLI v2** and credentials for the deploying user (`aws sts get-caller-identity` must work). The region is `ap-south-1` (Mumbai); set `AWS_REGION` to change it.
2. `jq`, `zip`, `rsync`, `git`, and `node` + `npm` (all normally present on a Mac with Homebrew).
3. Optional, only for `exec`: the Session Manager plugin (`brew install --cask session-manager-plugin`).
4. You do **not** need Docker: the image is built in AWS (CodeBuild).

## First deploy

```bash
make aws-deploy             # creates the network and registry stacks, then STOPS and tells you to fill the secret
make aws-secrets-from-env   # reads LORE_GEMINI_API_KEY, LORE_SLACK_WEBHOOK_URL, LORE_GITHUB_TOKEN from the root .env
#   or: make aws-secrets    # asks for them with hidden input instead
make aws-deploy             # builds the image, deploys the app, publishes the website, prints the URL
```

`make aws-secrets*` also generates `LORE_SESSION_SECRET` and `LORE_FALKORDB_PASSWORD` for you. Values are never printed, never put on a command line, and never written to git. The second `aws-deploy` takes about 30 to 45 minutes the first time (stacks about 10 min, CodeBuild 6 to 8 min, ECS 5 min, CloudFront 5 to 15 min). On first boot the API loads the Kettle data into the empty graph in the background (`LORE_LOAD_ON_START=if_empty`, a few minutes with real embeddings); watch it with `make aws-logs`.

## Day to day

| Task | Command |
|---|---|
| Check that it is healthy | `make aws-status` |
| Follow logs | `make aws-logs` (API) or `make aws-logs CONTAINER=falkordb` |
| Ship a backend change | commit, then `make aws-backend` (builds `:<git-sha>`, redeploys) |
| Ship a frontend change | `make aws-frontend` |
| Rotate a key | `make aws-secrets`, then `infra/deploy.sh restart` |
| Shell inside the API container | `infra/deploy.sh exec` (or `exec falkordb`) |
| Roll back | `infra/deploy.sh rollback` (lists tags), then `infra/deploy.sh rollback <tag>` |
| Try another Gemini model | `MODEL_PRO=gemini-4-argon infra/deploy.sh backend-only` |
| Delete everything | `make aws-destroy` (type `lore` to confirm) |

## Cost (ap-south-1, ARM64, approximate)

About **$2.2 per day** while it runs (Fargate 1 vCPU + 2 GB about $1.10, load balancer about $0.65, public IPv4 addresses about $0.36, everything else about $0.05). Roughly $66 for 30 days, plus Gemini usage (about $0.15 to $0.20 per investigation). A CodeBuild run costs a few cents. Details: INFRA_PLAN section 8. `make aws-destroy` stops all charges.

## Security in plain words

- **Nobody reaches the load balancer directly.** Its firewall accepts only CloudFront's published IP ranges, and its default answer is `403`. Only requests with the secret `X-Origin-Verify` header (added by our CloudFront, value in `lore/origin-verify`) are forwarded.
- **The database is not reachable from outside.** FalkorDB's port 6379 is never opened; the API reaches it on `localhost` inside the task, and it also needs a password.
- **The website bucket is private.** Only this CloudFront distribution can read it (Origin Access Control).
- **Secrets stay in Secrets Manager.** The task's execution role can read only `lore/app`. The app's own role can do nothing except open an ECS Exec shell and use its one EFS folder.
- **Weak spot to know about:** the CloudFront-to-ALB hop is plain HTTP (D-16: no certificate or domain, to keep the setup small). It is protected by the IP list and the secret header, but it is not encrypted on the way.
- **The public URL is open to anyone.** The per-visitor rate limit does not cap total Gemini spend (see HUMAN_REVIEW R-31).

## Things worth knowing

- **One task, on purpose.** A deploy stops the old task before starting the new one (about a minute of downtime): the run registry lives in memory, and two FalkorDB processes must never share one EFS folder.
- **FalkorDB's start script ignores command-line arguments.** The password and the journal setting are therefore passed through `REDIS_ARGS` (see the comment in `cfn/app.yaml`), not as a container command.
- **`CHANGE_ME` placeholders.** `lore/app` is created with them. CloudFormation writes them only when it creates the secret, so later updates never overwrite your real values, and `deploy.sh` refuses to deploy the app while any remain.
- **The graph and the data are not in git.** They live on EFS and are rebuilt from `backend/data` when the graph is empty. `make aws-destroy` deletes the EFS disk and the graph with it.
